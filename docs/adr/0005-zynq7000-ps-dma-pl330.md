# ADR 0005: Zynq-7000 PS DMA controller (ARM PL330) driver

- **Status:** Accepted (implemented, verified on hardware; see "Open items")
- **Issue:** [#3 `[P5][Medium]` ARM PL330 PS DMA driver](https://github.com/nick-fedchik/Zephyr-RTOS-PYNC-Z1/issues/3)
- **Zephyr version:** `v4.5.0`
- **Platform:** Digilent PYNQ-Z1 (Xilinx Zynq-7000 `XC7Z020`, dual Cortex-A9, 512 MiB DDR3)
- **Delivered as:** `patches/0007-drivers-dma-add-zynq7000-pl330.patch`
- **References:** Xilinx UG585 (chapter 9, DMA Controller), ARM PL330 TRM (DDI 0424),
  Linux `7.3.6` `drivers/dma/pl330.c`

## Context

The Zynq-7000 PS has an ARM PL330 DMA controller (`dmac_s`, `0xF8003000`, secure
manager) with 8 channels, 16 event/interrupt lines and 4 peripheral request
interfaces. Zephyr `v4.5.0` ships `drivers/dma/dma_pl330.c`, but it targets a
Broadcom integration: compatible `arm,dma-pl330`, a `microcode` memory region and
`control_regs` taken from the devicetree, a single hard-coded instance, polling
inside `dma_start()`, no completion interrupt, no cache maintenance and no
`dma_get_status()`.

Issue #3 asks for a `dma_driver_api` implementation with memory-to-memory
transfers, interrupt-driven completion, cache coherency on the Cortex-A9 DDR3
buffers and a basic `dma` driver test on `-b pynq_z1`.

Constraints are the same as in ADR 0001-0004: no Vivado, upstream changes as
numbered patches with disjoint hunks, nothing lab-specific in the repository.

## Decisions

### D1. A new driver with its own compatible, not an extension of `dma_pl330.c`

The existing driver would need an interrupt path, cache handling, status
reporting, instance-aware state and a different microcode strategy. That is a
rewrite, and the result would still be bound to the Broadcom bindings. The new
driver is `drivers/dma/dma_xlnx_zynq_pl330.c` with compatible
`xlnx,zynq-dma-pl330`, binding `dts/bindings/dma/xlnx,zynq-dma-pl330.yaml` and
Kconfig `DMA_XLNX_ZYNQ_PL330` (default `y` when a matching node is enabled,
selects `CACHE_MANAGEMENT`). Both drivers can coexist.

### D2. Interrupt driven; one event line per channel

Each channel `n` signals completion with `DMASEV` on event `n`. The DMAC raises
one SPI per event (events 0-3 = SPI 14-17, events 4-7 = SPI 40-43) plus the abort
line (SPI 13). All nine are described in the `dmac_s` node and share a single ISR:

- `FSRC` is read first. A faulting channel is killed (`DMAKILL`) and reported to
  the callback with `-EIO`.
- `INTMIS` is read next; each pending event is cleared in `INTCLR` and completes
  its channel: `INTEN` bit off, destination range invalidated, `total_copied`
  updated, `busy` cleared, callback called.

Events 8-15 are not used; they stay available for peripheral DMA.

### D3. Per-channel microcode generated at `dma_config()` time

The PL330 executes a small program from memory. The driver keeps a 512-byte,
cache-line-aligned program buffer per channel (`mcode[]`) and builds it when the
channel is configured:

- `DMAMOV SAR/DAR/CCR`, then nested `DMALP`/`DMALPEND` loops (up to 256 x 256
  iterations) around `DMALD`/`DMAST` bursts.
- The beat width is the widest (up to the 64-bit AXI bus) that both addresses are
  aligned to. The burst length comes from the MFIFO depth divided by the channel
  count (`CR0`/`CRD`), clamped to 1..16.
- The remainder is copied with one beat-width loop and one byte loop, so any
  length and any alignment of source and destination work.
- `DMARMB`/`DMAWMB` are emitted only before revision `r1p0`. The program ends with
  `DMAWMB`, `DMASEV` (event = channel) and `DMAEND`.
- Up to 4 chained blocks (`PL330_MAX_BLOCKS`) are concatenated in the same
  program.

The program is flushed to memory after generation. `dma_start()` writes
`DMAGO` through `DBGINST0/1` and `DBGCMD`; `dma_stop()` sends `DMAKILL` on the
channel thread.

### D4. Fixed addresses use single-beat bursts

`DMA_ADDR_ADJ_NO_CHANGE` on either side selects a fixed AXI address. It requires an
explicit power-of-two `source_data_size`/`dest_data_size` (not larger than the
bus), and the address and block length must be multiples of it; otherwise
`dma_config()` returns `-EINVAL`. The beat width is limited to that size.

On hardware a multi-beat FIXED burst reading DDR did not hold the address (each
4-byte source word appeared twice, then the source advanced). The cause is the DDR
path, not the microcode, so fixed sides are always programmed with a burst length of
1, where FIXED and INCR are the same single transfer. This costs throughput on
fixed addresses, which are not the target of this driver (peripheral FIFOs come
with the peripheral DMA follow-up).

### D5. Cache maintenance: L1 only, in the driver

The DMAC reads and writes memory behind the CPU caches. Zephyr maps DDR as normal
write-back cacheable memory. The PL310 L2 cache is off on this board
(`reg1_control` = 0), so only L1 maintenance is needed:

- `dma_start()`: clean the source range, clean+invalidate the destination range,
  then start.
- completion: invalidate the destination range before the callback.

Buffers should be 32-byte aligned and a multiple of 32 bytes. For unaligned edges
the architecture code cleans and invalidates the partial lines, which is safe as
long as no other agent touches those edge lines during the transfer. If L2 is ever
enabled, the driver has to add PL310 range operations (listed under open items).

### D6. MMIO mapping inside the driver

The driver uses `DEVICE_MMIO_ROM`/`DEVICE_MMIO_RAM` with `DEVICE_MMIO_MAP()` and
`K_MEM_CACHE_NONE` at init, so `soc.c` needs no MMU region entry. This keeps patch
0007 independent from patch 0002 and from the QSPI/watchdog region entries.

### D7. Secure manager

`DS` reads 0 on this board, so the manager is secure. The driver reads `DS[9]`
(`dns`) at init and sets the `SRCNS`/`DSTNS` bits in `CCR` and the `DMAGO` ns bit to
match, so it also works if the manager is ever non-secure.

### D8. Supported subset

Accepted: `MEMORY_TO_MEMORY`, 1-4 chained blocks, `INCREMENT` and `NO_CHANGE`
address adjustment, completion callback, `dma_stop()`, `dma_get_status()` and
`dma_get_attribute()` (`DMA_ATTR_BUFFER_ADDRESS_ALIGNMENT` = 1,
`DMA_ATTR_MAX_BLOCK_COUNT` = 4). `dma_get_status()` derives `pending_length` from
the channel `SA`/`DA` registers.

Rejected with `-ENOTSUP`/`-EINVAL`: peripheral directions, handshake, scatter and
gather, reload, cyclic, more than 4 blocks, zero-length blocks, channel numbers
outside 0..7. `dma_suspend()`/`dma_resume()` are not implemented, so the stock
suspend/resume test case is skipped.

### D9. Devicetree placement and AMP

The `dmac_s` node (`status = "disabled"`) goes into `zynq7000.dtsi` between `spi0`
and `spi1`. This is the only place whose neighbouring lines do not overlap the
hunks of patches 0003-0006, so `setup_and_build.sh` keeps being able to
reverse-check each patch independently. The board DTS enables it. The AMP overlay
(`amp/zephyr_cpu1/boards/pynq_z1.overlay`) disables it, because Linux on CPU0
owns the DMAC in that configuration.

### D10. Test commands in the application

`src/dma_test.c` adds a `dma` shell command set (built only when the driver is
enabled): `info`, `selftest [kib]`, `align`, `multi`, `chain`, `fill`, `stop`
and `neg`. AC3 is additionally checked with the stock Zephyr
`tests/drivers/dma/loop_transfer` suite, built with a `zephyr,user`
`dma-test-devs = <&dmac_s>` overlay.

## Consequences

Positive:

- Zephyr gets a real interrupt-driven DMA for the PS with the standard
  `dma_driver_api`, usable by any Zephyr subsystem or test.
- Arbitrary length and alignment work without caller constraints.
- All eight channels can run concurrently.
- No `soc.c` change and no dependency on other patches.

Negative:

- `dma_start()` pays for L1 maintenance on the whole source and destination ranges.
  For 1 MiB this is about half of the total transfer time (see Verification), so
  the CPU is free only for the rest of the transfer. Small transfers are not worth
  offloading.
- Fixed-address mode is slow (single beats) and limited to the data sizes the bus
  supports.
- The L2 cache (PL310) is not handled; the driver is correct only with L2 disabled.
- The DMAC fault path (abort IRQ, `FSRC`, `DMAKILL` from the ISR) is implemented
  but was not exercised on hardware, because provoking it safely needs a source
  address that the CPU maps and the interconnect rejects (see Open items).

## Verification

Hardware: PYNQ-Z1, standalone SMP build (`./setup_and_build.sh`), netboot over TFTP,
UART0 console. `./amp/build_amp.sh` still builds. All seven patches apply to a fresh
`v4.5.0` tree and reverse-check on the working tree.

Controller probe: `PL330 r1p0: 8 channels, 16 events, 64-bit bus, 128-beat MFIFO,
secure manager`.

Acceptance criteria:

| AC | Result |
|----|--------|
| AC1: >= 64 KiB DDR3 M2M with IRQ callback, byte-exact | `dma selftest` 1, 64, 256 and 1024 KiB: all byte-exact, completion by IRQ callback |
| AC2: faster than `memcpy` or frees the CPUs | See table below: 1.1x-2.6x faster than CPU `memcpy`; the CPU is free after `dma_start()` returns |
| AC3: basic `dma` driver test on `-b pynq_z1` | Stock `tests/drivers/dma/loop_transfer`: 2 passed, 0 failed, 1 skipped (`suspend_resume`, not supported) |

Throughput, DMA vs. CPU `memcpy` (single runs; the `memcpy` figures vary with cache
state, the first 64 KiB run was cold):

| Size | DMA total | DMA | `memcpy` | `dma_start()` returned after |
|------|-----------|-----|----------|------------------------------|
| 64 KiB | 548 us | 114 MiB/s | 43 MiB/s (cold) | 344 us |
| 64 KiB | 473 us | 132 MiB/s | 115 MiB/s | 210 us |
| 256 KiB | 1624 us | 153 MiB/s | 120 MiB/s | 884 us |
| 1 MiB | 6297 us | 158 MiB/s | 120 MiB/s | 3347 us |
| 1 MiB | 8079 us | 123 MiB/s | 113 MiB/s | 4938 us |

About 37-47 % of the transfer time is left for other work after `dma_start()`
returns; the rest is cache maintenance. (The shell command also prints a
loop-iteration based "free" percentage of about 3 %. That counter is not
calibrated and should not be used.)

Other commands:

- `dma align`: 17 fixed plus 300 random source/destination/length combinations on
  all eight channels, guard bytes intact.
- `dma multi`: 8 channels x 64 KiB at the same time, byte-exact, 166-174 MiB/s
  aggregate.
- `dma chain`: three chained blocks of 1000 + 4096 + 77 bytes, byte-exact.
- `dma fill`: 4096 bytes from a fixed 32-bit source (after D4).
- `dma stop`: abort a 1 MiB transfer part-way, then run a full 64 KiB copy on the
  same channel.
- `dma neg`: invalid configurations are rejected with the expected error codes.

Problems found and fixed during bring-up:

- Fixed-address fill returned a mix of the pattern and neighbouring words. Fixed
  sides now honour the configured data size and use single-beat bursts (D4).
- A first `dma err` test (source at `0xC0000000`) faulted the CPU, not the DMAC: the
  driver's own cache clean of the source range hit an unmapped address and halted
  the system (a hardware reset was needed). It was replaced by `dma neg`.

## Open items

- Provoke and verify the DMAC fault path: needs a source that the CPU maps (for the
  cache operation) but the interconnect rejects, for example a reserved
  peripheral window mapped for the test.
- Peripheral DMA (`DMAWFP`, `DMALDP`, `DMASTP`) using the four PS request
  interfaces, together with the fixed-address handling.
- Scatter/gather, reload, cyclic transfers, `dma_suspend`/`dma_resume`.
- Lower start overhead for large buffers (range maintenance dominates).
- PL310 L2 support if L2 is enabled, and an SLCR clock/reset check
  (`APER_CLK_CTRL` bit 0, `DMAC_RST_CTRL`) instead of relying on the first-stage
  firmware.
- 64-bit addresses are not needed on the 32-bit Zynq-7000 and are not supported.
